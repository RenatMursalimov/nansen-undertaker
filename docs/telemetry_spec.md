## Принцип: строку пишет `nansen_api`, а не вызывающий слой

Прежняя редакция этого абзаца утверждала обратное («пишет вызывающий слой, а не
`nansen_api`»), и это расходилось с кодом. Исправлено по `nansen/DIVERGENCE.md` §3: документ
и код говорили разное, а читатель кода верит документу.

Одна строка на один запрос к Nansen. Пишут **три функции клиента**, через которые проходит
каждый запрос:

| функция | где | когда пишет |
|---|---|---|
| `_http_post` | `nansen_api.py:719`, `record` на `nansen_api.py:763` | живой запрос, любой исход |
| `_cache_hit` | `nansen_api.py:711`, `record` на `nansen_api.py:716` | ответ отдан из кэша, сеть не тронута |
| `_agent_tele` | `nansen_api.py:235`, `record` на `nansen_api.py:242` | агент (`agent/fast`, `agent/expert`) |

В них сходятся четыре публичные двери клиента: `_post` (`nansen_api.py:658`),
`_post_beta` (`nansen_api.py:1623`), `ask_agent` (`nansen_api.py:132`),
`smart_money_netflow` (`nansen_api.py:266`).

**Одно исключение, и оно названо, а не замолчано.** Пятый поход в сеть живёт в
`credits_left` (`nansen_api.py:345`) — свой `httpx.post` в `/smart-money/netflow` ради
заголовка с остатком, и строки телеметрии он НЕ ПИШЕТ. Сегодня он недостижим: ветка стоит за
`force=True`, а оба вызывающих (`cost_tracker.py:460`, `oc_dm.py:2236`) идут без него — это
«мёртвый параметр» из §«Мёртвые ветки» аудита. Но параметр живой, и первый, кто передаст
`force=True`, получит НЕУЧТЁННЫЙ запрос к Nansen — ровно тот класс, ради которого врезка и
уехала в горловину. Либо звать оттуда `_http_post`, либо не оживлять `force` вовсе.

**Почему не у вызывающих.** Доказательство оплачено: `track('nansen')` был заведён «по
месту» ровно в одной точке из ~20, и поэтому все цифры расхода были занижены систематически.
Врезка у вызывающих — тот же дефект, размноженный двадцать раз, и забыть её в новой точке
физически возможно. В горловине — нет.

**Что вызывающий слой действительно даёт — только имя сценария.** Контекстный менеджер
`nansen_log.scene(name, uid)` (`nansen_log.py:183`): клиент не знает и не должен знать, каким
словом человек его позвал, а между гейтом и точкой вызова лежат чужие слои. Живых врезок
сегодня 25 (`oc_dm.py`, `oc_callbacks.py`, `oc_menu.py`, `oc_trends.py`, `oc_flows.py`,
`dm_module.py`). Чужое имя и отсутствие имени дают `scene=?` и отдельную строку «БЕЗ СЦЕНЫ» в
сводке — сцену НЕ УГАДЫВАЕМ.

Запись — **лучшее усилие**: любая ошибка телеметрии не имеет права сломать ответ человеку.

## Файл

```
<BOT_DIR>/nansen_telemetry.log        прод
<STAND_DIR>/nansen_telemetry.log   стенд
```

Формат — **JSON Lines**: один компактный JSON-объект на строку, `ensure_ascii=False`,
без переводов строки внутри значений.

Расширение `.log` выбрано не случайно: `.gitignore:22` содержит `*.log`, поэтому файл
физически не может попасть в коммит. Для `.jsonl` пришлось бы править `.gitignore`,
и один забытый `git add` вынес бы хэши пользователей в публичный репозиторий.

Ротация: суточная, `nansen_telemetry.log.YYYY-MM-DD`, хранить 30 дней. На объёмах конкурса
(оценка: до 5 тысяч строк в день) это единицы мегабайт.

## Поля строки

| Поле | Тип | Обязательное | Смысл |
|---|---|---|---|
| `ts` | str | да | ISO 8601 с зоной MSK, например `2026-09-18T14:03:11+03:00` |
| `scenario` | str | да | слаг из фиксированного списка ниже |
| `endpoint` | str | да | путь Nansen: `smart-money/netflow`, `agent/fast`, … |
| `trigger` | str | да | `btn` \| `cmd` \| `tool` \| `job` |
| `surface` | str | да | `dm` \| `hub` \| `public` \| `group` \| `job` |
| `latency_ms` | int | да | от начала вызова до готового ответа; при попадании в кэш — реальные единицы мс |
| `credits_est` | int | да | оценка списания, **передаётся явно** (см. ниже) |
| `credits_remaining` | int \| null | да | из заголовка `x-nansen-credits-remaining`, иначе `null` |
| `outcome` | str | да | из фиксированного списка ниже |
| `http_code` | int \| null | да | код ответа; `null` для кэша, таймаута, локального отказа |
| `cache_hit` | bool | да | ответ отдан из кэша, сеть не тронута |
| `empty` | bool | да | запрос прошёл, но данных нет. Отдельно от `outcome`, потому что «пусто» — это тоже успех запроса |
| `uid_hash` | str \| null | да | солёный хэш, 12 hex. **Не покидает сервер** |
| `repeat_n` | int | да | какой это по счёту запрос этого человека по этому сценарию за сутки (1 = первый) |

### `scenario` — фиксированный список

**Живой список — `nansen_log.SCENES` (`nansen_log.py:57-76`), и верить надо ему.** Сюда его
копию не переписываем: второй список слагов разошёлся бы с реестром на первой же правке, а
увидел бы это не тест, а человек, отфильтровавший лог по несуществующему имени.

Спека предлагала своё именование, реализация ТЗ B выбрала своё, и совпал ровно один слаг из
шестнадцати (`perp_leaders`). Это часть расхождения «вариант A против варианта B» из блока
выше, и решать его переименованием СЕЙЧАС нельзя: слаг стабильный, а переименование посреди
конкурса ломает сравнимость с его началом. Соответствие для читателя старых черновиков:

| спека предлагала | в коде | |
|---|---|---|
| `sm_netflow` | `smart_flows` | |
| `sm_holdings` | `smart_holdings` | |
| `wallet_dossier` / `wallet_dossier_premium` | `wallet_profile` / `wallet_profile_premium` | |
| `token_breakdown` / `deep_passport` | `token_check` | два слага спеки сведены в один |
| `perp_leaders` | `perp_leaders` | совпал |
| `pm_markets`, `pm_wallet`, `pm_market_leaders` | `polymarket` | **три сведены в один** |
| `agent_ask` | `agent_free` | |
| `trends_smart` | `trends` | |
| `backtest_candles` | `chart` | |
| `flow_backfill` | `admin_backfill` | |
| `digest_job` / `tweet_job` | `digest_cron` / `tweet_cron` | |
| — | `bare_address`, `who_bought_sold`, `token_info`, `counterparties`, `wallet_balance` | этих в спеке не было |

**Одна потеря названа числом, а не замолчана.** Три сценария рынков предсказаний
(`scenarios.md` §6, §7, §8) пишутся одним слагом `polymarket`, поэтому вопрос «какой из трёх
люди правда открывают» по логу НЕ ОТВЕЧАЕТСЯ — а это ровно тот отбор, ради которого восемь
сценариев и отбирались. Либо развести слаги до старта сбора, либо в заявке писать по этой
тройке «не измерено».

### `outcome` — фиксированный список

| Значение | Когда |
|---|---|
| `ok` | ответ получен, данные есть |
| `empty` | ответ получен, данных нет (`empty: true`) |
| `cache` | отдано из кэша |
| `http_error` | не-200, кроме 402 и 429 |
| `rate_limited` | 429 |
| `no_credits` | **402** — кредиты кончились |
| `timeout` | исключение транспорта, таймаут |
| `nokey` | ключ не задан |
| `quota_user` | отказ по суточному лимиту человека, запроса к Nansen не было |

`no_credits` требует, чтобы `_post` перестал сваливать все не-200 в `None`
(дефект A3-2 аудита). **Пока A3-2 не починен, значения `no_credits` и `rate_limited`
физически не могут появиться в логе** — они выродятся в `empty`. Это зависимость
B3 от B2, и её надо соблюсти в этом порядке, иначе телеметрия за первые дни конкурса
будет уверенно врать, что данных не было.

### `credits_est` — только явно

**Нельзя** брать значение из `PRICES['nansen']['avg_units']` (`cost_tracker.py:92`): там
стоит 200 — цена агента в режиме `fast`. Структурный вызов за 1 кредит запишется как 200,
ошибка в 200 раз, а вызов `agent/expert` за 750 — наоборот, занизится втрое с лишним, и
весь расчёт стоимости ответа (C4) уедет в обе стороны сразу.

Таблица уже заведена в коде — `nansen_log._EP_EST` (`nansen_log.py:101-109`) и
`_EP_UNKNOWN` (`nansen_log.py:115-122`), брать значения оттуда, а не переписывать сюда
второй копией. **Источник цен — официальная страница docs.nansen.ai/api/overview
(снято 14.09.2026), а не докстринги клиента**: те писались по документации годичной
давности и разошлись с реальностью в двух местах (`agent/expert` стоит 750, а не 200;
`tgm/indicators` — 5, а не 25).

| Эндпоинт | `credits_est` |
|---|---|
| `agent/expert` | 750 |
| `agent/fast` | 200 |
| `profiler/address/premium-labels` | 150 |
| `tgm/indicators`, `tgm/holders`, `tgm/pnl-leaderboard`, `perp-leaderboard` | 5 |
| `v1beta1 tgm/historical-token-ohlcv` | 5 |
| `v1beta1 tgm/historical-token-flow-summary` | 5 (за каждый день) |
| `smart-money/holdings` | 3 (в overview числа нет, докстринг «1-5») |
| `token-screener`, `tgm/flow-intelligence`, `tgm/who-bought-sold`, `tgm/token-information` | 1 |
| `smart-money/netflow`, `profiler/*` (не премиум), `prediction-market/*` | **не измерено** → писать `0` и считать в сводке отдельной строкой «вызовов с неизвестной ценой» |

Ноль вместо выдумки — сознательно. Лучше строка «184 вызова с неизвестной ценой», чем
красивая сумма, собранная из догадок. Когда Ren снимет Usage Analytics, эти клетки
заполняются и сводка пересчитывается по тому же логу.

При `cache_hit: true` → `credits_est: 0`. Это и есть измерение пользы кэша.

## Приватность

- `uid_hash` = первые 12 hex от `sha256(salt + str(uid))`. Соль в `NANSEN_TELEMETRY_SALT`,
  минимум 32 случайных байта, лежит рядом с прочими секретами и в репозиторий не попадает.
- Хэш нужен ровно для двух чисел: сколько **разных** людей за день и `repeat_n`.
  Восстановить по нему Telegram-id нельзя без соли.
- **В экспорт `uid_hash` не попадает.** Экспорт — только счётчики. Это делает
  `telemetry_rollup.py --export`, и он физически не выводит поле.
- Адреса кошельков, контракты, тикеры, текст вопросов — **в лог не пишутся**. Ни одного
  поля под них в схеме нет, и добавлять нельзя: адрес участника это его адрес.
  Примеры вопросов для C2 собираются отдельно и вручную, с согласия автора.
- Ключ Nansen в лог не попадает: в схеме нет поля, куда он мог бы просочиться,
  а `credits_remaining` — число.

## Точки записи

Этот раздел — про **живой код**, поэтому имена в нём тоже живые (`scene`, `out`, `cr`),
а не предложенные спекой.

Одна запись на **один HTTP-запрос**, не на один экран. Сценарий `token_check` даёт
**четыре** строки — четыре эндпоинта внутри `token_nansen_block_ex`: три в цикле
(`nansen_api.py:1366`) и топ-PnL следом (`nansen_api.py:1376`), с одним `scene`. Иначе цена
сценария в **16** кредитов (`tgm/flow-intelligence` 1 + `tgm/indicators` 5 + `tgm/holders` 5
+ `tgm/pnl-leaderboard` 5, реестр `nansen_log.py:101-109`) не сойдётся с суммой по
эндпоинтам. **Прежняя редакция абзаца говорила «40 кредитов»** — число из докстрингов
клиента, которые разошлись с площадкой; исправлено по тому же разбору, что и остальные цены
(`DIVERGENCE.md:223`).

Сценарий `admin_backfill` (`oc_flows.py:146`) даёт по строке на каждый день цикла: цикл на
`oc_flows.py:155`, запрос внутри него на `oc_flows.py:162`, по 5 кредитов за день
(`tgm/historical-token-flow-summary`, `nansen_log.py:105`) — именно так видно, что 90 дней
это 450 кредитов. Потолок цикла 180 дней (`oc_flows.py:32`), то есть 900 кредитов за один
владельческий запуск.

Отказ по суточному лимиту (`out=quota_user`) пишется **до** обращения к Nansen
(`nansen_log.py:464`), с `cr=0`, `est=0` и `http=0` — не `null`: в формате `k=v` пустое
значение и ноль неразличимы, поэтому ноль здесь означает «в сеть не ходили», а не «код
ответа ноль». Это отдельный класс отказа по требованию B2, и без него не посчитать, сколько
людей упёрлось в лимит — а это главный аргумент за докупку кредитов.

## Сводка

Скрипт `nansen/telemetry_rollup.py`. Читает лог, печатает дневную сводку.

```bash
python3 nansen/telemetry_rollup.py                       # за сегодня
python3 nansen/telemetry_rollup.py --day 2026-09-18
python3 nansen/telemetry_rollup.py --since 2026-09-15 --until 2026-09-27
python3 nansen/telemetry_rollup.py --json                # для служебного чата
python3 nansen/telemetry_rollup.py --export nansen/submission/telemetry.md
```

Сводка обязана содержать (требования B3 и C2):

- запросов всего и по сценариям;
- кредитов сожжено (плюс отдельной строкой — вызовы с неизвестной ценой);
- разных людей (по `uid_hash`, само значение не печатается);
- ошибок по классам, отдельной строкой — честные отказы (`no_credits`, `quota_user`);
- доля пустых ответов;
- средняя и p95 латентность;
- доля попаданий в кэш;
- самый частый сценарий дня и самый дорогой запрос дня в кредитах;
- остаток кредитов на конец дня (последний непустой `credits_remaining`).

`--export` даёт таблицу за период для заявки и статьи, **без** `uid_hash` и без адресов.
